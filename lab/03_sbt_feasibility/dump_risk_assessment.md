# 基于真实 `.dump` 的 CFG 结构化还原风险复核结论（现阶段）

目的：针对“PTX 原生方案（CFG 结构化还原 + 硬件分歧/收敛）是否会被真实 Ventus 汇编中的控制流形态卡住”的担忧，基于现有测例产生的 `.dump` （objdump反汇编）进行事实复核；仅做分析，不涉及实现与修改。

## 样本范围

- `ventus-env/rodinia/opencl/*/*.dump`：7 份
- `ventus-env/testcases/_get_case/*/*.dump`：21 份
- 合计：28 份 `.dump`

## 关注的“硬门槛”风险点（对应 `simtstack_hardware.md` 的输入约束）

1. `CSR_RPC`/join 点是否能在静态层面解析为“函数内确定 label/PC”。
2. 是否存在会破坏结构化还原的控制流形态（例如 kernel 内的 `jalr` 间接跳转、无法定位的 join、明显的不可结构化跳转模式）。
3. `setrpc` 目标是否真实落在 `join` 指令位置（防止“计算得出 rpc，但代码中并无该 join”）。

## 复核结果（基于 28 份 `.dump` 的统计与抽样核查）

### 1) `setrpc`/`CSR_RPC` 的静态可解析性：满足

- 在所有 `.dump` 中，`vbranch`（`vb*`）前都能观察到紧邻的 `auipc t1, 0` + `setrpc ..., t1, imm` 模式：join 点表达为“当前 PC + 立即数”，属于纯静态形式。
- 所有出现的 `setrpc` 都是 `setrpc <rd>, t1, <imm>` 这一形式，未发现其它寄存器作为 `rs1` 的情况。

### 2) `setrpc` 计算得到的 `rpc` 与 `join` 的对应关系：满足

- 对每个 `.dump` 中的每一处 `auipc t1, 0` + `setrpc ..., t1, imm`，计算 `rpc = auipc_pc + imm` 后，都能在该 `.dump` 中找到 `rpc` 地址处存在 `join` 指令。
- 测例中存在 `imm` 为负值的情况（即 `rpc` 可能“小于”当前 `pc`，表现为 backward join），但仍满足“可静态解析、可定位 join”的要求。

### 3) 间接跳转/不可结构化控制流：未发现会阻塞的证据

- `jalr` 在 28 份 `.dump` 中均只出现在 `_start` 的固定位置（`0x8000009c`）用于启动阶段跳转到入口；在 kernel/辅助函数体内部未观察到额外的 `jalr`（因此未见 jump table / 函数指针调用等会破坏结构化还原的典型模式）。
- 汇编整体形态呈现常见的 `.LBB*` 基本块结构（配合标量 `j/beq/bltu/...` 与向量 `vb*`），未见“join 无法定位/控制流高度动态化”的直接迹象。

## 结论（现阶段）

基于上述两组真实测例（共 28 份 `.dump`）的复核结果：

- `CSR_RPC`/join 点在当前测例中**都可静态解析并可定位到明确的 `join` 指令地址**；
- 未发现会在现阶段阻塞 CFG 结构化还原的“典型不可控控制流形态”（尤其是 kernel 内 `jalr` 等间接跳转）。

因此可以将“CFG 结构化还原的硬门槛与不稳态导致不可控”的风险，在**现阶段测例覆盖范围内**判定为**可控**。

## 边界与注意事项

- 本结论仅对“当前收集到的 `.dump` 测例形态”成立，不代表所有未来 kernel/编译器版本输出都满足同样约束。
- 由于存在 backward join（负偏移 `setrpc`），结构化还原的判定/实现不应隐含“join 必须向前”的假设；若实现选择限制该形态，应明确将其纳入“不可结构化 → 回退”的条件。
