# Ventus 函数调用/返回：在 PTX 上的模拟方案（SBT 分析）

本文只做分析，不涉及实现；目标是在当前原型阶段补齐“函数调用”这块的可行性论证与输入约束。

核心矛盾：
- Ventus/RISC-V 视角：`jal/jalr` 本质是“写入 ra + 跳转到（可能是运行时计算的）目标 PC”。
- PTX 视角：`bra` 的目标必须是静态 label；但 PTX 提供 `.func`/`call`/`ret` 的调用机制，并且在常见工具链下可见“通过寄存器的间接 call”（需要 `.callprototype`）。

因此，“函数调用”的处理可以拆成两部分讨论：
1) **控制转移如何做**（call/return/间接跳转）
2) **调用约定（参数/返回值/栈帧）如何保持等价**（寄存器与内存语义）

---

## 0. 结论（推荐路线）

原型阶段推荐采用 **混合方案**：
- **控制转移**：尽量用 PTX 原生 `call/ret` 承载 Ventus 的“函数调用/返回”。
- **参数/返回值与栈**：不强行套 PTX ABI，而是把 Ventus 的寄存器文件/栈/内存视图当作“被模拟状态”，按 Ventus 行为自然读写（参数在寄存器/栈上怎么传就怎么传）。

同时写清楚一组输入约束，让这条路在“可证正确”的范围内先跑通：
- `jalr` 的用途受限：只用于函数返回（`jalr x0, x1, 0`）以及（可选）有限形式的函数指针调用；不用于跳表/任意 computed goto。
- 不要求支持非标准返回：返回目标必须是静态 callsite（即“从某个调用点进入的函数，最终回到该调用点的下一条”）。
- 调用深度有限（不递归或递归深度很浅）。

当输入不满足这些约束时，回退到“PC 调度器（解释器式 dispatch）”方案。

---

## 1. PTX 侧与本问题相关的能力边界

### 1.1 `bra` 不能表达 “PC = reg”

PTX 的分支（`bra`/`@p bra`）目标是静态 label，无法直接把 Ventus 的 `jalr rd, rs1, imm` 翻成 “跳到 `rs1+imm` 指向的任意地址”。

这就是 README 中提到的“computed goto 难题”的实质：不是“call 不行”，而是“任意间接跳转不行”。

### 1.2 `call/ret` 能覆盖大多数“函数调用/返回”

PTX 提供：
- `.func`：设备端函数实体
- `call`/`call.uni`：调用（含参数/返回值的 param 区编排）
- `ret`：返回到静态 callsite

并且在常见 CUDA 工具链生成的 PTX 中可观察到“通过寄存器的间接 call”形态（`call (..), %rdX, (..), prototype;`），这意味着**函数指针调用存在被承载的可能**。

关键点：无论 direct 还是 indirect 的 `call`，`ret` 仍然是“回到本次 callsite 的下一条”，它并不能表达“根据 ra 寄存器的值跳回任意位置”。

---

## 2. 被模拟状态：与调用约定相关的最小集合

无论采用哪种方案，都建议明确一个“被模拟状态”抽象（实现可以是内存结构体、SSA 变量或寄存器缓存，这里只定义语义）：

- 标量寄存器 `x[0..255]`（至少包含 `x1(ra)` 与 `x2(sp)`）（Ventus将RISC-V标量寄存器扩展到255个）
- 向量寄存器 `v[0..N)`（函数调用本身不直接依赖，但实际代码会跨调用使用）
- 关键 CSR（例如 `CSR_LDS/CSR_PDS/CSR_KNL/...` 与 `CSR_RPC`）
- （可选）逻辑 PC：用于 `auipc`/`setrpc` 等 PC 相关语义的求值或调试

“完全使用 Ventus 调用约定”的含义可以落到一句话：
- **参数/返回值在 Ventus 中放哪里，翻译后就仍然在被模拟状态的相同位置出现**；PTX 只负责承载控制转移与算术/访存的执行。

---

## 3. 方案 A（推荐）：混合方案 = PTX `call/ret` + Ventus ABI 语义

### 3.1 总体结构

- 每个 Ventus 函数（按 ELF 符号或分析得到的函数边界）翻译为一个 PTX `.func`（或 `.entry` 作为 kernel 入口）。
- 每个 PTX 函数接收一个“状态指针”（例如 `ctx`），内部把 `ctx` 中的寄存器/CSR 读入临时寄存器计算，必要时回写。
- 函数间调用用 PTX `call`，返回用 PTX `ret`。

这样，**控制转移由 PTX 保证**；而“ra/sp/参数/返回值”仍然体现在 `ctx` 的寄存器文件与内存访存上。

### 3.2 指令级翻译规则（只覆盖与调用相关的部分）

#### 3.2.1 直接调用：`jal x1, target`

目标：保持两件事等价：
1) Ventus 语义写入 `x1 = pc+4`
2) 控制转移进入 `target`，并在返回后继续执行下一条

做法：
- 在 `ctx.x1` 中写入“Ventus 逻辑地址意义下的返回地址”（`pc+4`）。
- 发出 PTX `call` 到被翻译的 callee `.func`。
- `call` 返回后，PTX 自然落到下一条；并且 `ctx.x1` 保持为 `pc+4`（除非 callee 按 Ventus 语义修改了它）。

#### 3.2.2 直接调用但不写 ra：`jal x0, target`（tail-call 形态）

Ventus 语义不会更新 ra。

在 PTX 侧最简单的等价实现是：
- 不写 `ctx.x1`
- 仍 `call target`
- 紧跟一个 `ret`（等价于“调用后立刻返回给本函数的 callsite”）

是否允许把它优化成跳转（真正 tail-call）不影响正确性，但属于实现优化，不在本文讨论范围。

#### 3.2.3 返回：`jalr x0, x1, 0`

在输入约束成立（“返回目标必须是静态 callsite 的下一条”）时，可以把该指令翻译为 PTX 的 `ret`。

注意：这一步**没有**真正使用 `ctx.x1` 作为控制流目标；`ctx.x1` 仅作为被模拟状态的一部分保留，以满足“程序可能读 ra”的语义。

若未来需要对“非标准返回”（ra 被改写）保持语义，则必须回退方案 B（PC 调度器）。

#### 3.2.4 函数指针调用（可选）：`jalr x1, rs1, imm`

若要支持有限形式的函数指针调用，需要同时满足：
- `rs1 + imm` 的结果在运行时落在“某个已翻译函数入口集合”内
- 能把该目标映射到 PTX 侧的函数地址（或等价句柄）

可行的工程化约束是：
- 只支持“由重定位/符号表可识别”的函数地址来源（例如取某个函数符号地址、从表中加载函数地址），不支持完全任意的整型构造。

在满足上述约束时，可以使用 PTX 间接 `call`（配合 `.callprototype`）来承载控制转移，同时仍按 Ventus 语义写 `ctx.x1 = pc+4`。

### 3.3 函数边界与符号需求（原型阶段建议写死的输入前提）

为了把 Ventus 函数映射成 PTX `.func`，你需要函数边界信息。原型阶段建议明确要求：
- 输入 ELF 未剥离，包含 `.symtab`，并且函数符号为 `STT_FUNC`；
- 或者输入来自受控工具链，能够提供函数列表（链接脚本/元数据）。

若函数边界不可得，只能回退方案 B：把整个程序翻译成“单个大函数 + PC 调度器”。

### 3.4 该方案的收益与已知限制

收益：
- 不需要在 PTX 侧实现“任意 PC 跳转”，规避 `bra` 的根本限制。
- 返回天然正确（PTX call stack），不需要维护软件调用栈（除非你要做调试/异常语义）。
- 与“参数/返回值走 Ventus 栈/寄存器”的想法兼容：PTX ABI 只作为承载机制，不作为语义基准。

限制（必须写进可行性分析，避免隐性假设）：
- 无法覆盖 “return 到任意地址”（ra 被运行时改写）的语义。
- 无法覆盖 `jalr` 被用作跳表/任意 computed goto 的语义。
- 调用深度与 PTX/硬件的实际支持有关；原型阶段建议把“无递归/浅递归”作为约束。

## 4. 方案 B（兜底）：PC 调度器（解释器式 dispatch）

当输入程序存在以下任一情况时，方案 A 不再稳健：
- `jalr` 用于跳表/间接跳转（不止函数指针 call）
- ra 被改写导致“非标准返回”
- 函数边界不可得或不可置信

PC 调度器的思路是：把控制流也当成“被模拟状态”，显式维护 `pc`，并在一个大循环里按 `pc` 分发到对应基本块：
- `jal`：把 `ret_pc` 入软件栈（或写入 `ctx.x1` 并另存一份用于控制流），`pc = target`
- `jalr`：`pc = (rs1 + imm)`（真正按计算结果跳转）
- `ret`：从软件栈弹出 `pc`

该方案可表达性最强，但代价通常是：
- dispatch 结构膨胀（大量 `@p bra` 链或多级表）
- 影响性能与寄存器压力

因此更适合作为“语义兜底”而非默认路径。

---

## 5. 建议的原型验证闭环（只验证调用相关语义）

建议把“能否跑通”的验证拆成由易到难的三层（仍不涉及具体实现，只定义应该测什么）：

1) 仅 direct `jal` + 标准 `ret`：验证 ra 写入正确、跨函数的寄存器/栈读写保持一致。
2) `jal x0, target`（尾调用形态）：验证不写 ra 仍能正确返回。
3) （可选）受控函数指针 call：验证“目标集合可解析”时能正确间接调用；否则应明确拒绝或回退到方案 B。
